# Phase 6, Design contract: Demande de téléchargement par email

Branch `design/06-contract` (from `milestone/v1.1`). Scope: UI/UX/copy only. No app code. Decisions D-01..D-14 in `.planning/phases/MILESTONE-v1.1-DECISIONS.md` are inputs and are not reopened. Double opt-in screens and the download landing page (P7, P9) are out of scope.

Artifacts: `tokens.css`, `app.css`, `screens/*.html` (generated by `_tools/build.mjs`), `gallery.html`, `MOCKUPS.md`, `06-DESIGN-CRITIQUE.md`. Measurements: `_tools/measure.mjs` -> `_tools/measure-report.json`.

## 1. Flow and surfaces

1. Visitor adds photos to the selection (existing cart buttons on album and portfolio pages). Cart drawer footer CTA changes from "TÉLÉCHARGER LES PHOTOS" to **"RECEVOIR PAR EMAIL"** (`a-cart-list`).
2. CTA switches the same drawer to the **request step** (no second modal, no route change). The old donation modal is no longer a gate (see critique Q1).
3. Submit -> server action `requestDownload` -> always the same generic success screen (`a-success`), unless validation fails, the IP is rate limited, or the server errors.
4. Private album: visitor without a key lands on `/mon-album` (existing route), enters the key (screens `b-*`), then sees the album and uses the same selection and request flow. The key never appears in a URL.
5. Visitor gets one transactional email (`c-email-*`) with a button to `/telechargement/[token]`.

Single primary action per screen: cart list = "Recevoir par email"; request = "Envoyer le lien"; success = "Fermer"; key = "Accéder à mon album".

## 3. Components

- **Drawer** (`.drawer`): right panel `min(440px,100vw)`; at <= 600 px full screen. Header (eyebrow, title, 44x44 close), scrolling body, sticky footer holding the primary button. `role="dialog" aria-modal="true" aria-labelledby`. Escape closes. Focus moves to the title on open, returns to the cart FAB on close. Body scroll locked (existing behaviour).
- **Selection summary**: up to 3 thumbnails (64 px wide, 3:2) + "+N", count text, "Modifier la sélection" text button (44 px tall) returning to the list.
- **Email field**: visible label above (never placeholder-only), `type=email inputmode=email autocomplete=email autocapitalize=none spellcheck=false`, height 52 px, hint below, error replaces hint and is linked through `aria-describedby`, `aria-invalid=true`.
- **Honeypot**: field `website`, off-screen (not `display:none`), `aria-hidden=true tabindex=-1 autocomplete=off`. Never shown. Server also checks a signed render timestamp (min 2 s) and ignores silently.
- **Newsletter box** (D-01): `<input type=checkbox name=newsletter>` default unchecked, never `required`, full row is the label (min 44 px), 24 px visual box. Wording in section 5. Disabled only while submitting.
- **Primary button**: 52 px, gold, uppercase. Loading = disabled + spinner + "ENVOI EN COURS…", `aria-busy` on the form, inputs `readonly` (not disabled, so values and focus survive).
- **Message** (`.msg`): icon + text, `role="alert"` for errors (assertive), `role="status"` for success (polite). Left-stripe borders are not used (full 1 px border + tinted background).
- **Key field**: password-type by default, show/hide toggle 44x44 with `aria-pressed` and changing `aria-label`, monospace, `autocomplete=off`, never prefilled from URL.
- **Image placeholders**: diagonal tint block labelled with its ratio ("3:2"), used only in prototypes. Production uses the real thumbnails with `next/image`.

## 6. Responsive and breakpoints

- <= 600 px: drawer is full screen (100vw x 100dvh), body scrolls, submit stays pinned in the footer; background page hidden.
- 601 px and up: drawer 440 px on the right over the scrim.
- Key page: content column max 480 px, centred, 24 px side padding, 48 px top (32 px on mobile).
- Email: 600 px max, fluid below; at <= 480 px card padding 20 px and title 30 px.
- Use `100dvh`, `env(safe-area-inset-bottom)` on the pinned footer. Landscape phones: body scrolls, footer remains reachable. Verified at 390 and 1440 only; 320 px and tablet are acceptance checks AC-14 and AC-15 to run in the build.

## 7. Behaviour contract (UI <-> server)

`requestDownload` returns only: `{ok:true}` (generic) | `{ok:false, code:'invalid_email'}` | `{ok:false, code:'rate_limited'}` | `{ok:false, code:'server_error'}`. Never reveals whether an email is known or subscribed, never differs by newsletter state, never echoes the address.
- Honeypot filled, render time under 2 s, or per-EMAIL limit hit: return `{ok:true}` and send nothing (indistinguishable from success). Per-IP limit: `rate_limited`.
- Private album key: `{ok:true}` | `{ok:false, code:'invalid_key', attemptsLeft}` | `{ok:false, code:'locked'}`. Same message for unknown and wrong key. Constant-time compare. Key travels in a POST body only.
- Cart snapshot sent = `[{photoId, source}]` + `albumId` (CartContext v2). The UI never sends file URLs.

## 8. Motion and reduced motion

- Drawer slide 350 ms `cubic-bezier(.22,1,.36,1)` (unchanged); scrim fade 300 ms; success panel rise 8 px + fade 350 ms; button color 150 ms; spinner 0.8 s linear. Only `transform`/`opacity` animate.
- `prefers-reduced-motion: reduce`: all durations about 0, drawer appears without slide, spinner replaced by a static dotted ring, text label still says "ENVOI EN COURS…" (state is never conveyed by motion alone).

## 9. Accessibility

WCAG 2.2 AA target. Visible labels on all fields; error text linked with `aria-describedby`, `role=alert`; success `role=status aria-live=polite`; focus ring 2 px `--focus` on all controls; focus trap inside the open drawer; Escape closes; tab order = visual order; checkbox row is one label; honeypot out of the tab order and the accessibility tree; touch targets >= 44x44 (inline links inside sentences are exempt under 2.5.8); colour is never the only error signal (icon + text); text zoom to 200% must not clip (drawer body scrolls); email has real text (no image-only content), `lang` attribute, semantic `role=article`, `role=presentation` on layout tables.

## 10. Legal wording constraints (RGPD / CNIL, from D-01, D-02, PITFALLS 1)

1. Newsletter box is separate, optional, **never pre-ticked**, never required, and the submit button text is the same whether ticked or not.
2. The sentence describes one purpose (newsletter) and names the sender ("Ghjulianu Codani"); the download purpose is stated separately in the privacy line.
3. States that consent is optional, that a confirmation email follows (double opt-in), and that unsubscribe is one click.
4. Privacy line links to the FR/EN privacy policy (P5) and states purpose of the email; no email is added to the newsletter list without the later confirmation.
5. Text is versioned (`CONSENT_TEXT_VERSION = 'v1'`); if any consent wording above changes, bump the version. The exact strings shown must be the ones stored with the consent.
6. The download email must not contain marketing content or a newsletter pitch. It contains a "this message only relates to your request" line, a privacy link, and the publisher postal address (LCEN; placeholder in the mockup, owner to fill).
7. No dark patterns: no countdown pressure, no "are you sure you don't want…" friction on the unticked box.
